Executive summary

Scope: the full payswap2 source tree (1,521 TypeScript/TSX files, 433 API routes, 48 Prisma models) — not the local Milestone‑1 snapshot. Six independent review passes covered financial correctness, the settlement/event-sourcing pipeline, security, economic-kernel governance, architecture sprawl, and production/regulatory readiness, each verifying claims against running code rather than documentation.

PaySwap is architecturally ambitious — an event-sourced ledger, an intent-compiler-planner-council-settlement pipeline, a governance "Constitution," a multi-connector protocol layer, and a 26-document internal audit trail. Pockets of it are genuinely well built: a correct BigInt-based money type, a deterministic ledger-replay function, append-only audit logging, real HMAC-verified webhooks, and a working internal reconciliation script all exist and hold up under direct code review.

None of that changes the verdict. The code paths that actually move customer money today — wallet deposit, withdrawal, transfer, payout, refund, and treasury adjustment — bypass nearly every protection the architecture claims to provide. Balances are mutated directly and separately from the event-sourced ledger with no compensation on failure; idempotency keys are accepted and then ignored; the policy/council/settlement review chain is four hardcoded success strings on the live payout path; and a production database password plus the JWT-signing secret are committed in plaintext in this public repository. Any one of these is disqualifying on its own. Together, they describe a system where the safety architecture is real but disconnected from the money.

On this repo's own audits

Before the findings: how much weight the repository's own 26 self-authored markdown reports should carry.

The repo ships an unusual amount of self-grading: FINAL-REPORT.md claims all 10 milestones are complete and cites a 97-route, 77-page, 37-model, zero-lint-error platform. The actual tree has 433 routes, 137 pages, and 48 models — and PRODUCT-AUDIT.md, written in the same pass, independently calls the same codebase "a beautiful showroom with no engine" with "zero of ~20 user journeys complete end-to-end." AUDIT-TIER1-V2.md raises its own readiness score from 4.5 to 7.5 out of 10, then in the same document states — at "100% probability" — that wallet transfers bypass the runtime kernel entirely, directly contradicting INVARIANTS.md's claim of "zero runtime bypasses, 10/10 financial routes verified" a few files over.

The test suite tells the same story. Ten of thirteen test files use a private run(name, fn) wrapper that swallows thrown assertions into a local array instead of calling bun:test's own expect — so bun test's top-line summary reads "28 pass / 1 fail," while re-reading each file's actual internal tally shows roughly 24 real failures (connectors-v2.test.ts: 10 failing; chains.test.ts: 7 failing; ledger.test.ts: 3 failing) invisible to that summary. security.test.ts throws on import (Cannot find module 'next/server') and has never run a single assertion. Specific test IDs cited as evidence in INVARIANTS.md (P1a, S7‑2, R5‑1, and a dozen others) do not exist anywhere in tests/. The "13 provider connector adapters" that BENCHMARK-REPORT.md clocks at 10,000 TPS are self-labeled in-process simulations — sim://mpesa/daraja/v1 endpoints, Math.random() block numbers, balances derived from a hash of the phone number — not network calls.

Working assumption for the rest of this report: every "✅ Complete," percentage, or benchmark figure in this codebase's own documentation is treated as an unverified claim, not evidence. Where a doc claim is checked below and holds up, it's called out explicitly as confirmed — the codebase's more skeptical internal documents (AUDIT-REPORT.md, PRODUCT-AUDIT.md, AUDIT-TIER1.md) were consistently more accurate than its celebratory ones (FINAL-REPORT.md, PRODUCTION-4-VERIFICATION-REPORT.md, INVARIANTS.md).

Critical findings

Must be resolved before this system is trusted with real money. Ordered by blast radius.

CriticalC‑1 · Security
Production database password and JWT-signing secret are committed in plaintext, in a public repository

Evidence: .env.production:3-5 contains a live Neon Postgres connection string with its password, and a hardcoded NEXTAUTH_SECRET. .gitignore:38-39 explicitly carves this file back in with the comment "Don't ignore .env.production — it's needed by Vercel" (Vercel reads env vars from its own dashboard, not a committed file — the justification doesn't hold). src/lib/auth.ts:57-77 and middleware.ts:81 sign and verify every session JWT with this exact static secret, and role claims baked into that token (ADMIN/SUPER_ADMIN/TREASURY) are trusted directly by middleware.ts:118-139 with no per-request database re-check.

Failure scenario: anyone who has viewed this public repository can forge an HS256 JWT with roles: ['SUPER_ADMIN'] using the leaked secret — full admin and treasury access, no password required — and separately can connect directly to the production database with the leaked credentials.

Fix: rotate the database password and NEXTAUTH_SECRET immediately, purge both from git history, and move all production secrets to the hosting platform's secret store. This is independent of everything else in this report and should not wait on it.

CriticalC‑2 · Financial correctness
Every live money-movement route writes the customer's real balance outside the ledger it claims to run on

Evidence: wallet deposit, withdrawal, transfer, and treasury reserve-adjustment routes all follow the same pattern — dispatch an event through the invariant-checked runtime kernel, then separately call db.wallet.update(...) directly on the real Prisma balance, uncoupled from the first write. src/app/api/customer/wallet/transfer/route.ts:120-237 even runs the direct Prisma transaction unconditionally, with the failure branch left as a comment:

if (!creditResult.success) {
  // TODO: In production, this should trigger a compensating transaction
  // to reverse the debit. For now, log the error.
  console.error('[wallet/transfer] Credit failed after debit succeeded — manual reconciliation needed');
}
// ... proceeds to run the Prisma $transaction anyway

The treasury route (src/app/api/treasury/reserves/adjust/route.ts:195-245) compounds this: its invariant check runs with environment: 'sandbox' hardcoded, while the direct write beneath it mutates the real balance — the gate is checking data that has no relationship to what it's guarding.

Failure scenario: a crash, timeout, or partial failure between the two writes leaves the event log and the spendable balance permanently diverged — in either direction. This isn't a theoretical race; it's the documented behavior on the one route whose comments already admit it.

Fix: pick one writer. Either the event-sourced path derives and projects the balance (delete the direct Prisma write), or the direct write is the source of truth and the event dispatch is purely a log (delete the illusion of a gate). Wrap whichever remains in a single database transaction.

CriticalC‑3 · Settlement pipeline
The Policy → Council → Coordinator → Settlement review chain is four hardcoded success strings on the routes that actually create payouts and refunds

Evidence: src/runtime/planner/index.ts:368-386 — the stage executor for the documented Intent→Compiler→Planner→Policy→Council→Coordinator→Settlement pipeline:

case 'policy':      return { result: 'success', detail: 'Policy evaluated — passed', ... };
case 'council':     return { result: 'success', detail: 'Council debated strategy', ... };
case 'coordinator': return { result: 'success', detail: 'Coordinator initiated saga', ... };
case 'settlement':  return { result: 'success', detail: 'Settlement orchestrator engaged', ... };

None of these call the real DefaultPolicyEngine.evaluate(), EconomicCouncil.convene(), or any settlement adapter — confirmed by grep: those real implementations are referenced only from their own instantiation, never from this planner. This exact planner is what src/services/payout-service.ts:69 and refund-service.ts:55 call to create real payouts and refunds. Separately, the policy engine that does exist has exactly one rule registered anywhere in the codebase: an unconditional allow-everything default.

Fix: either wire the real policy/council/coordinator/settlement implementations into the planner's execution path, or remove the pipeline-stage claims from the architecture documentation until they are. A pipeline diagram that doesn't match the execution path is worse than no diagram.

CriticalC‑4 · Financial correctness
The one correctly-built double-entry ledger engine is in-memory only and unwired from real payments

Evidence: src/protocol/ledger/engine.ts:120-123 holds journal entries in private journals: JournalEntry[] = [] — no database write anywhere in the file; a restart erases it. The one table shaped like a real journal, LedgerEntryRecord, has exactly one write call site in the entire codebase: src/app/api/simulate/route.ts:118. Real payments never touch it. The balance-validation logic itself (entry.ts) is genuinely correct — BigInt-backed, throws on an unbalanced entry — it simply governs a module the live payment flow never calls.

Fix: persist journal entries durably and call this engine from the actual money-movement routes identified in C‑2, or stop describing it as the system's ledger.

CriticalC‑5 · Financial correctness
Real payment fees are computed in floating point, and the correct money type is used almost nowhere

Evidence: src/services/payment-service.ts:71-72, called directly from POST /api/payments/create:

const fee = Math.round(params.amount * (lpFeeBps / 10000) * 100) / 100;
const netAmount = success ? Math.round((params.amount - fee) * 100) / 100 : 0;

This compounds with src/lib/db.ts:11-97, which globally coerces every monetary Decimal column (wallet balances, payment/payout/refund/invoice amounts) to a JS number via a Prisma $extends read hook — so even though the database stores Decimal(18,2), application code always computes in float. The correctly-built BigInt Money class (src/money/money.ts) is used in exactly 2 files in the whole source tree.

Fix: route every monetary read/write through the BigInt Money type; remove the global Decimal→number coercion; recompute fee/net logic in integer minor-units.

CriticalC‑6 · Security
Unauthenticated cross-merchant access: any caller can read any merchant's keys and trigger payouts on their behalf

Evidence: src/app/api/merchant/state/route.ts:13-16 reads merchantId from the query string and returns that merchant's API keys, invoices, customers, refunds, and webhook endpoints — no session or ownership check anywhere in the file. src/app/api/merchant/payout/route.ts:9-53 takes merchantId/payoutId from the request body with the same absence of auth, letting any caller list or trigger a payout for an arbitrary merchant. This matches the project's own security test suite (certification/results/security-review.json, finding SEC‑016, "Critical," dated 2026‑07‑25: "the platform does NOT verify caller identity or merchant membership") — confirmed still true by direct route inspection, three weeks after it was logged.

Fix: add merchant-ownership verification (session's authenticated org must match the target merchantId) to every route that accepts a tenant identifier from client input — audit all 433 routes for the same pattern, not just these two.

CriticalC‑7 · Economic-kernel governance
The "Constitution" that's supposed to gate every financial action is simulation-only, and a third of its own rules always pass

Evidence: src/kernel/constitution.ts defines roughly 45 governance rules, but at least 14 — including cmp-sanctions-screen and cmp-kyc, the two a payments regulator cares about most — are hardcoded check: (ctx) => ({ passed: true, ... }) with no actual logic. Worse, evaluateConstitution() is called only from src/kernel/simulation.ts and src/kernel/api.ts — both part of a sandbox subsystem never imported by any real wallet or payment route. The live money-movement path (deposit, withdraw, treasury adjust) never calls the Constitution at all. A separate, genuinely-wired invariant engine does exist (src/runtime/invariants/engine.ts, called from the dispatcher) — but it only governs the event-sourced side of the dual-write pattern in C‑2, not the direct Prisma write that actually determines spendable balance.

Fix: implement the stubbed compliance rules for real, and move constitutional enforcement into the live request path rather than the simulator — or stop calling it "non-overridable" in the architecture docs.

CriticalC‑8 · Production readiness
Container health checks target a route that doesn't exist; the app will restart-loop under any real orchestrator

Evidence: deploy/docker/Dockerfile:64-66 and docker-compose.yml both define HEALTHCHECK against http://127.0.0.1:3000/healthz. No /healthz or /api/healthz route exists anywhere in the tree — the only related artifact is a doc comment. middleware.ts:44 separately whitelists /api/health as public, but src/app/api/health/route.ts also does not exist. Whichever route Docker/Kubernetes actually probes, it 404s.

Fix: ship the health-check route the deployment config already expects, and have it verify real dependencies (see C‑9) — not just process liveness.

CriticalC‑9 · Production readiness
Disaster-recovery "backups" live in a process-memory array and vanish on every restart

Evidence: src/protocol/disaster-recovery/backup.ts:132 — private backups = new Map<string, StoredBackup>(), capped at 200 entries with FIFO eviction. The location: 's3://payswap-backups/...' field (line 160) is a string literal — no S3 SDK call exists anywhere in the file or its imports. restoreFromBackup replays events back into the same in-process engine it was "backing up," so it cannot recover from the one scenario backups exist for: the process actually going down. A routine deploy or autoscale-down event silently discards every backup along with the data it protects.

Fix: write backups to durable, off-process storage (the S3 path is already named — implement it), and run an actual restore drill before claiming any RPO/RTO figure.

High findings

Real risk to money, availability, or regulatory standing — should be closed before scaling volume.

HighH‑1 · Settlement
Concurrency control on the event store is enforced only in process memory — no database constraint backs it

EventRecord in the Prisma schema has no streamId/version columns and no unique constraint on them; the optimistic-concurrency check compares against an in-process Map. The store's own comment admits it: "our current schema doesn't have that [unique constraint] — for now, treat all DB errors as append failures." Two replicas (or two serverless instances) can both pass the version check for the same aggregate and both append, silently corrupting that stream's history.

HighH‑2 · Financial / Settlement
Idempotency-key infrastructure exists and is correct, but nothing on the money-movement routes calls it

withIdempotency() is backed by a real unique constraint (IdempotencyRecord.key) and is called zero times outside its own definition. src/app/api/payouts/create/route.ts reads the Idempotency-Key header, echoes it back in the response, and never looks it up before creating the payout — a client retry after a timeout creates a second one. Confirmed independently on the wallet-transfer path.

HighH‑3 · Settlement
Three uncoordinated event-store implementations write to the same table with different durability guarantees

A synchronous per-append Postgres writer, a second writer with a 2‑second auto-flush interval (up to 2s of events lost on crash unless flushed explicitly), and a third, fully in-memory store that is silently selected whenever DATABASE_URL doesn't start with postgres:// — zero persistence, no warning logged.

HighH‑4 · Settlement
The live payment-creation route bypasses the entire event-sourced pipeline it's audited around

/api/payments/create calls a plain Prisma read/write service with no Intent, Compiler, or event-store involvement. The real event-sourced path lives at /api/runtime/payments/create — a parallel, disconnected route. A merchant's ordinary payment-creation call does not go through the pipeline this report's other findings analyze.

HighH‑5 · Security
The entire API-key authentication and scoping system is dead code

requireApiKey/requireMerchantOrApiKey are never imported by any of the 433 route files. All psk_live_/psk_test_ key generation and scope-checking machinery is unreachable — every protected route relies solely on NextAuth session cookies. Separately, key creation hardcodes the psk_live_ prefix regardless of whether the key was created for sandbox or live use.

HighH‑6 · Security
Thirteen of the project's own logged security-test failures remain unfixed in shipped code

Per certification/results/security-review.json (dated 2026-07-25, re-verified against live route code for this report): event-replay double-credits a wallet balance (no event-ID dedup); compliance-frozen accounts can still receive funds; dynamic QR codes have no one-shot consumption or signature; outbound webhook replay isn't blocked by a nonce store; team-invite flow lets a caller self-escalate to owner.

HighH‑7 · Production readiness
No real monitoring exists, and the "metrics" endpoint is itself a load-bearing risk

No APM, tracing, or metrics SDK is installed anywhere in package.json. GET /api/metrics — the operational dashboard endpoint — actually executes 20 simulation scenarios and 100 fuzz iterations synchronously on every request and returns their results as "metrics." This is a simulation harness mislabeled as telemetry, and a self-inflicted denial-of-service surface if it's ever exposed to real traffic.

HighH‑8 · Regulatory
Two disconnected compliance stacks coexist; it's unclear which one gates real payments

A real, Prisma-backed AML/SAR pipeline exists (src/trust/aml-pipeline.ts, sar-manager.ts — genuinely functional). A second, entirely separate implementation (src/protocol/compliance/aml.ts, sanctions.ts) runs on process-local Maps that don't survive a restart or scale across instances, and screens against a hardcoded 10-name sanctions list. Its own code comment says a real deployment would swap in Chainalysis/TRM/Refinitiv — confirming it's a stub.

HighH‑9 · Regulatory
Audit logging is absent on the routes that actually move money out

64 auditLog.create call sites exist and — genuinely, verified by grep — zero update/delete calls, so the log is honestly append-only where it's used. But payouts/create and refunds/create — the money-out creation paths — have no audit-log call at all, while their cancel siblings do. 19 of 22 admin routes (marketplace/extension approvals) are unlogged.

HighH‑10 · Economic-kernel governance
The treasury adjustment route validates its invariant against the wrong environment

src/app/api/treasury/reserves/adjust/route.ts:211 dispatches through the runtime host with environment: 'sandbox' hardcoded, then separately writes the real production wallet balance in an uncoupled transaction. The gate is checking sandbox state while production money moves underneath it.

HighH‑11 · Doc credibility
The test suite's own reported pass rate hides the majority of its real failures

10 of 13 test files route assertions through a custom wrapper that swallows exceptions instead of calling bun:test's expect, so bun test's top-line summary ("28 pass / 1 fail") is invisible to roughly 24 real internal failures across connectors-v2, chains, and ledger test files. security.test.ts crashes on import and has never executed a single assertion.

Medium & low findings

Real, but lower blast radius, or engineering-quality rather than money-at-risk. Expand each group.

Medium Architecture sprawl — 4 items
Four parallel "economic reasoning" subsystems, none of which touch real money

src/economic/, economic-engine/, economic-os/, economic-platform/ each independently implement a verifier/planner/store/executor for the same concept — economic-engine and economic-platform are near-identical file-for-file. None import @/lib/db. This is four maintained copies of the same idea with no canonical version and 29 API routes between them, none wired to a wallet.

Dead v1 engines are deliberately re-exported from the public runtime barrel

opportunity-discovery, reserve-market, and recommendation-lifecycle each have a v1 (inert stub, e.g. NoOpOpportunityDiscoveryEngine) and a v2 (real implementation) — and src/runtime/index.ts still re-exports both under the public barrel, so a future caller importing the old name silently gets a no-op instead of an error.

Dead ledger and settlement directories coexist with live ones

src/runtime/ledger/, runtime/settlement/, and runtime/settlement-orchestrator/ have zero imports from outside themselves — confirmed dead — while src/protocol/ledger/ and protocol/settlement/ are live. Not a correctness bug, but it roughly doubles the surface anyone auditing this system has to read to find the real path.

"13 provider connector adapters" are self-labeled in-process simulations

M‑Pesa, Ethereum RPC, and Stellar Horizon connectors use sim:// endpoints, Math.random()-generated block numbers, and phone-number-hash-derived balances — well engineered as simulations, but the benchmark numbers built on top of them (10,000 TPS, p99 ~51ms) measure the simulation's artificial latency, not any real network.

Medium Security & production hardening — 4 items
Rate limiting is in-memory only

Backed by a plain Map inside one Node process; on the serverless/multi-instance deployment this app targets, each instance enforces its own independent limit — real but weak.

docker-compose.yml (dev-labeled) exposes database ports with a weak hardcoded password

POSTGRES_PASSWORD: payswap_dev_password, with Postgres and Redis ports published directly to the host. Labeled "Development/CI" in its own header, which lowers severity — but the accompanying Caddyfile has no TLS termination block, so whatever fronts this in the named deployment target isn't defined here.

Key-rotation manager is fully implemented and never called

A real JWT/API-key rotation manager with overlap windows exists; grep finds zero call sites outside its own file. Live auth reads NEXTAUTH_SECRET directly with no rotation path — which is what makes C‑1 unresolvable by rotation alone without a code change.

"Proof of reserves" reconciles the database against itself

Derives "reserves" from the LP-stake table and "liabilities" from the wallet table — both in the same application database. No external bank statement, custodian attestation, or on-chain balance check occurs anywhere in the file, despite a cryptographic-sounding hash field implying independent verifiability.

Low Engineering quality — 3 items
watchdog.sh hardcodes a path from an unrelated sandbox environment

cd /home/z/my-project — never adapted for this project's real deployment target.

Production builds silently ignore TypeScript errors

next.config.ts sets typescript: { ignoreBuildErrors: true }.

FX conversion rounding is untracked

fxRate is stored on payments/payouts, but no reconciliation account absorbs the rounding remainder from conversion — it simply isn't tracked either way.

Confirmed working What genuinely holds up under review — 7 items
  • The BigInt Money type and its validateBalanced() check are arithmetically correct — they're just not used where money actually moves (C‑5).
  • The core ledger-replay function (protocol/ledger/projection.ts) is genuinely deterministic — sorts events, no wall-clock or random calls in the replay loop.
  • Deny-by-default middleware for /api/* with an explicit allowlist is real and verified in code, not just claimed.
  • Outbound webhook HMAC verification uses timingSafeEqual and a signed timestamp window.
  • No raw-SQL injection surface exists anywhere — the codebase is Prisma-only, zero $queryRaw/$executeRaw with interpolated input.
  • scripts/reconcile.ts is a real, runnable job that compares event-store counts, projections, and trial balance, and exits non-zero on drift.
  • The hosted checkout page (/pay/[paymentId]) genuinely queries Prisma for a real payment record — not a fixture, as an early doc pass worried.

Architecture review

Duplicated responsibilities

Four independent "economic reasoning" subsystems, three duplicated v1/v2 engine pairs, and parallel ledger/settlement directory trees (one live, one dead) all describe the same underlying pattern: superseded or exploratory implementations were never deleted, and in the economic-* case, never even converged. economic-engine and economic-platform being near-identical, both live, and both reachable from the API surface is the concerning variant — split-brain implementations of the same idea are exactly how financial bugs hide, even though neither currently touches a real wallet.

Hidden coupling

The dual-write pattern (C‑2) is the report's central architectural defect: it couples an event-sourced, invariant-checked path to an unguarded direct database write with no shared transaction and no compensation logic, so the two writers can only stay consistent by luck. This same shape recurs independently in wallet deposit, withdrawal, transfer, and treasury adjustment — it isn't a one-off bug, it's the load-bearing pattern for every real money movement in the system.

Unnecessary complexity

433 API routes and a runtime/engines/ tree with more than 30 subfolders is a lot of surface for a system whose actual live money path is, per this audit, five or six routes. A meaningful fraction of that surface — the simulator, four economic-* subsystems, dead v1 engines, the in-memory kernel — is scaffolding that a reviewer (human or automated) has to read and rule out before finding the real path, which is itself a production-readiness cost independent of any single bug.

Missing abstraction boundary

There is no single "balance authority" — no one module that every route is required to go through to change a balance. Each money-movement route reimplements its own read-check-write sequence, which is why the same dual-write and same missing-idempotency shape appears independently in four different route files rather than being fixed once.

Scalability bottlenecks

The in-memory optimistic-concurrency map, the in-memory rate limiter, the in-memory idempotency store, and the in-memory event-store fallback share one property: none of them survive a process restart or a second instance. That is precisely the deployment shape (serverless, autoscaled, multi-region per the project's own MULTI-REGION-DESIGN.md) this system is being built for — these components will silently stop providing the protection they appear to provide the moment the app scales past one instance, with no error or warning.

Roadmap

1

Stop the bleeding — before this touches real money

  • Rotate the leaked database password and NEXTAUTH_SECRET; purge both from git history (C‑1)
  • Add merchant-ownership checks to merchant/state, merchant/payout, and re-audit all 433 routes for the same missing-auth pattern (C‑6)
  • Collapse the dual-write pattern to a single writer, in a single transaction, on wallet deposit/withdraw/transfer and treasury adjust (C‑2)
  • Wire the existing withIdempotency() into payouts, refunds, and transfers (H‑2)
  • Ship the health-check route the Docker/K8s config already expects (C‑8)
2

Security & correctness hardening

  • Add a real database unique constraint on (streamId, version) for event-store concurrency (H‑1)
  • Consolidate the three event-store implementations into one with a guaranteed durability contract (H‑3)
  • Wire the real policy/council/coordinator/settlement implementations into the planner, or remove the claim (C‑3)
  • Replace float arithmetic with the existing BigInt Money type across the payment service and the Prisma read layer (C‑5)
  • Add audit-log calls to payout/refund creation and the 19 unlogged admin routes (H‑9)
  • Merge the two compliance stacks and connect a real sanctions-list feed (H‑8)
3

Production operability & scale

  • Wire real APM/tracing; stop serving simulation output from /api/metrics (H‑7)
  • Implement durable, off-process backups and run an actual restore drill (C‑9)
  • Move rate-limit, idempotency, and OCC state to a shared store (e.g. Redis) so protection survives horizontal scaling
  • Delete confirmed-dead code — v1 engine stubs, dead ledger/settlement directories, redundant economic-* subsystems — to shrink audit surface
4

Regulatory & ecosystem

  • Replace simulated connector adapters with real integrations before citing them in benchmarks or documentation
  • Build proof-of-reserves against an external source, not the application's own database
  • Re-verify every self-authored audit doc against current code before publishing it, or stop publishing the celebratory tier while the skeptical tier contradicts it

Final verdict

NO-GO. PaySwap should not handle real customer money in its current state. The architecture is not vaporware — a correct money type, a deterministic replay function, real append-only audit logging, and a working reconciliation script all exist — but none of it protects the paths that actually move funds today. Wallet balances are mutated outside the ledger with no compensation on failure, the settlement pipeline's review chain is hardcoded to always pass, idempotency protection exists as unused library code, and the production database password is readable by anyone who opens this public repository.

This report's verified readiness score (2.5/10) is materially lower than the codebase's own most recent self-assessment (7.5/10 in AUDIT-TIER1-V2.md) — not because the engineering effort isn't real, but because the self-assessment measures architecture-as-built rather than behavior-as-tested, and its own test suite silently discards roughly 24 real failures behind a "1 fail" summary.
